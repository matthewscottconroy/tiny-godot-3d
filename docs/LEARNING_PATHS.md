# Learning paths

The index in the root README is a reference: demos in categories, all equal.
That is the right shape when you already know what you are looking for and the
wrong shape when you don't.

These are ordered routes through the same demos. Each one builds toward a
recognisable kind of 3D game, and each step assumes the ones before it.

The collection is still small, so the routes are short. They are here anyway,
and in this shape from the start, because the order is the part that is hard to
add later: every demo on a path also gets a "Related demos" link from its
neighbours, generated by `tools/build_index.py`, and a path nobody wrote produces
a collection of islands. What each route is *missing* is listed under it, so the
next demo to write is never a guess. See [known gaps](GAPS.md) for the full list.

**Difficulty** is marked per step, and means how much is going on in the file,
not how clever it is:

- 🟢 **Starter** — one idea, nothing assumed.
- 🟡 **Working** — several pieces interacting; assumes you can read a
  `CharacterBody3D` script without looking things up.
- 🔴 **Deep** — an algorithm or an architecture, worth reading twice.

## 1. Move a character around a 3D world

The most-travelled route, and the one where 3D differs most from 2D: there is no
single "forward" any more, so movement and camera stop being separable problems.

| # | Demo | | What it adds |
|---|------|---|--------------|
| 1 | [character-controller-3d](../character-controller-3d) | 🟡 | Gravity, jumping and coyote time on a `CharacterBody3D`, with the rules split out of the body so they can be tested |
| 2 | [orbit-camera](../orbit-camera) | 🟡 | A third-person rig, pitch limits, and movement expressed relative to where the camera is looking |
| 3 | [spring-arm-camera](../spring-arm-camera) | 🟡 | The same camera, but colliding with the level — and the asymmetric smoothing that stops it flicking |
| 4 | [first-person-controller](../first-person-controller) | 🟡 | The other camera entirely: mouse capture, head bob, and a view model |
| 5 | [gamepad-3d](../gamepad-3d) | 🟡 | The same movement from an analogue stick, and the deadzone that makes it feel like one |
| 6 | [shape-cast-3d](../shape-cast-3d) | 🔴 | Why the character stops dead at a kerb, and the two casts that tell a step from a wall |
| 7 | [character-push](../character-push) | 🟡 | Making the world notice: shoving what you walk into, with mass that means something |

**Missing from this path:** root motion, and a character that can be pushed
*back*.

## Where to start if you have written 2D Godot

Read [character-controller-3d](../character-controller-3d) first. The motor is
deliberately the same shape as a 2D controller, so what stands out is only what
actually changed: three axes, a floor normal instead of a floor direction, and
`move_and_slide()` resolving against surfaces rather than lines.

Then read [orbit-camera](../orbit-camera), which is where the differences stop
being cosmetic. A 2D camera follows a position; a 3D camera has an orientation
that the player's input has to be expressed in terms of, and getting that
backwards is the most common way a third-person prototype ends up feeling wrong
without anyone being able to say why.

After that, [lights-and-shadows](../lights-and-shadows) — because the thing with
no 2D counterpart at all is that a correct scene can render completely black,
and the thing that makes a 3D scene expensive is not the polygons.
